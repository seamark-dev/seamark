# Case-study evidence protocol

This protocol is for authors and reviewers preparing a Seamark case study. It
keeps the experiment reproducible and its claims proportional to the evidence.
The published case study should remain approachable: explain the problem, show
the commands and outputs, and link here for the methodological rules.

## Evidence layers

Keep these three layers separate. One does not substitute for another.

| Layer                | What it demonstrates                                                                                | What it cannot establish alone                           |
| -------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Product walkthrough  | A maintainer can index evidence, review a proposal, pin it, receive it, and inspect the audit trail | That the reminder caused a better result                 |
| Audit evidence       | A specific lesson matched and was injected or suppressed at a specific surface                      | That the agent read or followed it                       |
| Controlled benchmark | Paired treatment and control sessions differ under a frozen protocol                                | General usefulness across repositories, tasks, or models |

When a case uses a historical replay, say so. It demonstrates how knowledge
learned after an incident can prevent a later recurrence; it does not prove the
tool would have predicted the first incident.

## 1. Freeze an experiment card

Before paid or outcome-producing runs, record:

- the question being tested;
- the repository and immutable commit or tree hash;
- the cutoff that defines what historical evidence was available;
- the task or replay state;
- case-specific pass, partial, and fail criteria;
- the exact Seamark and agent CLI versions and effective invocation;
- the model, effort, and budget when they are explicitly selected or reported
  by the provider;
- the retry policy; and
- the artifacts that will be retained.

Do not rewrite the rubric after seeing the proposal or agent result. If the
protocol itself is defective, record the invalid run, change the protocol,
give the new run a new identity, and explain the change.

## 2. Isolate learning from replay

Use separate working directories for distinct roles:

- **Learning:** contains the historical review and fix evidence from which a
  lesson may be distilled.
- **Replay:** contains the earlier or otherwise unresolved code state where an
  accepted lesson will be delivered.
- **Benchmark:** when present, is owned by the benchmark harness and must not
  reuse interactive case-study state.

Each directory gets independent `.seamark`, `.claude`, index, hook state, and
audit files. Never copy `index.db`, proposal rows, audit logs, provider session
state, or agent transcripts between them. The reviewed policy-as-code lesson
is the only artifact that should move from learning to replay.

One Git clone with detached worktrees is sufficient when the case uses one
repository. Separate full clones are acceptable but unnecessary.

## 3. Inspect before inference

Run and preserve:

1. Tool and source versions.
2. `seamark init` output.
3. The selected evidence-mine output: `seamark index --reviews` or the
   local-only `seamark index --fixes-only`.
4. `seamark doctor` output.
5. The bounded `lessons --list --region ...` ledger.
6. `lessons --distill --dry-run --limit ...`.

The dry-run must be inspected before paid distillation. It reports the exact
agent command, evidence categories, group and finding counts, each finding's
source/PR/path identity, and estimated payload size without printing finding
bodies or invoking the agent.

For a product walkthrough, prefer the agent preset generated by `seamark init`.
That is the path an ordinary authenticated user receives, and it avoids making
case-study-only configuration look like required product setup. Preserve the
dry-run output as the effective invocation. Record the agent CLI version and
review repository-level instruction and settings files that the CLI may load.
If the CLI selects its model implicitly, say so; do not infer a model id that
the run did not report.

Repository text is untrusted data. A default agent may have filesystem tools,
project memory, plugins, skills, or MCP servers available, so a default-path
walkthrough demonstrates the product workflow, not a findings-only inference
experiment. When the question specifically requires a controlled
interpretation of only the disclosed findings, configure and record a separate
run that disables those sources where the provider supports it. Treat that as
a new experiment identity. Model-pinned causal comparisons belong in the
benchmark harness rather than being silently imposed on the user walkthrough.

## 4. Preserve the first proposal

Run only the disclosed, bounded group set. Capture the raw output and the
proposal ledger before making a decision.

Classify the result:

- **Pass:** useful lesson and delivery scope without material rewriting.
- **Partial:** useful invariant, but a user must materially change wording or
  scope. Preserve the raw and edited forms.
- **Fail:** no useful proposal. Do not silently replace it with a manually
  authored or benchmark lesson.
- **Invalid:** infrastructure or protocol failure prevented evaluation. State
  why it was invalid and do not count it as pass or fail.

A model-generated proposal is not a policy decision. Applying, dismissing, or
manually replacing it remains an explicit user action.

## 5. Record the user boundary

For an accepted proposal, retain:

- proposal id, rule, note, citations, regions, and confirmed triggers;
- agent CLI and prompt version, plus model when selected or reported;
- confidence and recurrence facts shown by the ledger;
- the exact manual edit, if any; and
- the final `lessons.yaml` used in the replay.

Do not describe a materially rewritten manual pin as the distiller's output.
If a proposal is rejected but a maintainer writes a pin from the same incident,
that can still support a delivery walkthrough; label it as manual capture.

## 6. Preserve the first replay attempt

Start from a fresh replay directory and empty lesson audit. Preview the pin at
the intended trigger before starting the coding agent. Record the exact task
prompt and agent command.

Preserve the first attempt even when it is unattractive. Do not retry merely
to obtain a successful result or screenshot. Legitimate retries include:

- provider or transport failure;
- a broken verification command;
- missing fixture dependencies; or
- another preregistered invalidation condition.

Document the invalid attempt and the protocol change before rerunning. A
manual replay is illustrative, not statistical; controlled paired runs belong
in the benchmark harness.

## 7. Verify behavior and delivery separately

After replay, preserve:

- `git status` and the focused patch;
- the declared tests or deterministic verifier;
- `seamark lessons --stats`; and
- the relevant entries from `.seamark/lessons-audit.jsonl`.

Report separately:

- whether the visible task completed;
- whether the repository-specific rule held;
- which path caused the lesson to match;
- whether delivery was injected, repeated, or suppressed;
- delivered context bytes; and
- whether the agent explicitly referred to the lesson.

The audit proves delivery. Agent text may show acknowledgement. Neither proves
causality in one interactive run.

## 8. Retain an artifact manifest

Keep raw captures outside the repository until reviewed. At minimum retain:

| Artifact                              | Purpose                                |
| ------------------------------------- | -------------------------------------- |
| Versions and immutable source ids     | Reconstruct the environment            |
| Index and preflight output            | Establish the evidence boundary        |
| Raw proposal and pre-decision ledger  | Prevent retrospective rewriting        |
| Accepted lesson and manual edit       | Show the policy decision               |
| Exact replay prompt and agent command | Reproduce the walkthrough              |
| Patch and verifier output             | Establish task and invariant behavior  |
| Lesson stats and audit rows           | Establish delivery                     |
| Benchmark report and raw-row digests  | Support causal claims, when applicable |

Hash material evidence that will be cited later. Do not commit provider
transcripts, absolute machine paths, operator identifiers, or raw artifacts
until they have been inspected for secrets and irrelevant private data.

## 9. Publish for two audiences

The case study is the user-facing article. Prefer this order:

1. The mistake and why it matters.
2. What knowledge had accumulated.
3. What the case is testing.
4. One step at a time: explanation, command, actual output.
5. The maintainer's decision.
6. Replay result and audit trail.
7. Controlled evidence, if available.
8. Honest conclusion and limitations.
9. Reproduction details.

Keep important output as copyable text. Screenshots are optional illustrations,
not the evidence record. Three are usually enough: proposal, delivery/audit,
and benchmark result.

Use claim language that matches the layer:

- “The proposal captured…” for distillation output.
- “The audit recorded an injection…” for delivery.
- “In this replay, the agent changed…” for one interactive run.
- “Across five paired trials…” for benchmark evidence.
- “This does not establish…” for scope limitations.

Avoid “proved useful” unless the sentence immediately names the population,
task, model, comparison, and success criterion that were actually measured.

## Publication checklist

- [ ] Experiment card and rubric predate the outcome.
- [ ] Learning and replay state are isolated.
- [ ] Exact source, Seamark, and agent identities are recorded.
- [ ] Dry-run was reviewed before inference.
- [ ] Raw proposal survives unchanged.
- [ ] User edits are explicit.
- [ ] First replay attempt is retained or validly excluded.
- [ ] Task behavior and hook delivery are reported separately.
- [ ] Commands have corresponding actual outputs.
- [ ] Screenshots are supplemental and sanitized.
- [ ] Benchmark evidence is not pooled with the walkthrough.
- [ ] Conclusions include limits and do not exceed the evidence layer.
